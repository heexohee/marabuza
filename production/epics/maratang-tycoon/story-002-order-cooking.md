## 완료 조건

*`design/game-brief.md`(목표 & 실패 조건 + MVP 기능 3–4)에서 이 스토리 범위만 가져옴:*

- [ ] 주문에는 조리 방식이 있다: 마라탕(육수) 또는 샹궈(볶음)
- [ ] 주문에는 맵기 단계가 있다 (`src/js/data.js`의 기존 0–4단계 `SPICE_LEVELS`를 그대로 사용)
- [ ] 주문에는 땅콩소스 여부(예/아니오)가 있다
- [ ] 100g당 단가는 마라탕 1,800원, 샹궈 3,000원이다 (스토리 001 가격 공식에 쓰임)
- [ ] 조리 방식마다 "적정 조리 시간 구간"(최소~최대 초)이 따로 있고, 두 구간은 다르다 (샹궈는 볶음이라 마라탕보다 빨리 익음)
- [ ] 구간이 시작되기 전이나 끝난 뒤에 건지면 품질이 떨어지고, 구간 안에서 건지면 정상 품질이다
- [ ] 품질 저하 결과는 반환되는 상태에서 정상 품질과 구분된다 (스토리 004의 서빙·정산 로직이 이를 반영할 수 있도록)

## 예외 상황
- 구간이 시작되는 초나 끝나는 초에 정확히 건짐 — 경계 포함, 정상 품질로 처리
- 조리를 시작한 뒤 주문의 조리 방식을 바꾸는 것은 범위 밖 — 조리가 시작되면 방식은 고정

## 구현 메모

이 단계에는 ADR이 없으니, 위 완료 조건대로 바로 구현한다.

지금 `src/js/logic.js`의 `cookTime(s)`는 모든 그릇에 같은 조리 시간 하나를 쓴다. 이 스토리에서 조리 방식별 구간(`windowStart`, `windowEnd` 두 값)으로 바꾼다. 상태의 `pots` 배열(`src/js/logic.js`의 `startCooking`/`servePot` 참고)은 이미 냄비마다 `remaining`/`total`을 가지고 있다. 배열 구조를 바꾸지 말고, 냄비 기록에 주문의 조리 방식과 계산된 구간을 추가한다.

맵기 부분은 `SPICE_LEVELS`와 `scoreBowl`의 기존 맵기 불일치 벌점 방식을 그대로 쓴다. 맵기 단계를 새로 만들지 않는다.

**성능**: 성능 영향 없음 — 냄비 몇 개의 시간 비교뿐이다.
