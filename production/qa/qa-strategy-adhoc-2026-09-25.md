## 2. 항목별 분류 근거 및 완료 조건 공백

- **계산대**: story-001 문서에 완료 조건 8개, 예외 상황 3개가 명시됨 (Logic 유형 확정). `qa.level: minimal`이라 증거가 "권장"으로 완화되어 있지만 실제로는 이미 자동 테스트 + UI 스크린샷 둘 다 존재 — 사실상 BLOCKING 기준 충족.
- **클라우드 세이브**: 스토리 문서 자체가 없음. "완료"의 기준(로그인 성공률, 동기화 지연 허용치, 오프라인 폴백 동작)이 어디에도 정의돼 있지 않아 — QA가 합/불을 판단할 근거가 없음. 최소한 완료 조건 문서화를 `/story-readiness` 전에 요청해야 함.
- **픽셀아트/상점 정렬**: 둘 다 스토리 문서 없이 진행됨. Visual/Feel과 UI는 기본적으로 BLOCKING이지만, 게이트가 요구하는 "리드 sign-off"가 스크린샷 파일명/디렉터리만으로는 확인 안 됨 — 별도 sign-off 기록(리드 승인자, 날짜) 필요.

## 3. 코드/테스트 리뷰로 찾은 구체적 커버리지 공백 및 리스크

### 계산대 (`src/js/logic.js`, `src/js/ui.js`)
- `confirmCharge`의 exact/overcharge/undercharge 세 분기 모두 유닛테스트 있음 — 공백 없음.
- `adjustCharge`가 0 미만으로 못 내려가는 경계는 테스트됨(`test_checkout_adjust_charge_never_goes_below_zero`); 그러나 **매우 큰 값으로 올리는 상한 테스트는 없음** (실수로 여러 번 클릭 시 청구액이 비정상적으로 커질 수 있는지 UI 레벨에서 미검증).
- `checkoutOutcome`에서 `chargedAmount === correctPrice`를 부동소수점 비교 없이 정수 비교만 하므로 100원 단위 반올림 체계상 문제는 없어 보이나, `round100` 결과가 항상 정수인지에 의존 — 이 전제가 깨지면(향후 소수 단가 도입 시) 침묵 실패 위험.
- 결제 대기 중 하루 종료 차단은 테스트됨(`test_checkout_day_does_not_end_while_checkout_pending`) — 공백 없음.
- `checkoutHtml`(ui.js)의 실제 렌더링(예: "소고기 ×N" 표기, 버튼 비활성화 조건)은 유닛테스트 대상이 아니며 스크린샷 1~2장으로만 확인됨 — 리스트에 항목이 많을 때(꼬치+소고기+양고기+고수 동시)의 레이아웃 확인 스크린샷 없음.

### 저장/클라우드 (`src/js/save.js`, `src/js/cloud.js`, `src/js/main.js`, `src/js/screens.js`)
- `pushSave` **실패 분기(서버 upsert 에러) 미테스트** — 테스트는 성공/로그아웃 두 경우만 커버. `main.js`의 `persist()`는 `pushSave`가 `false`를 반환하면 "클라우드 저장에 실패했어요. 이 기기에는 저장됐어요" 토스트를 띄움(오케스트레이터 코드 확인으로 정정). 단 **`pushSave`가 예외를 던지면(reject) `.catch`가 없어 침묵 실패** — 알림 없이 unhandled rejection.
- `pullSave`가 `error`를 반환하는 경우(네트워크 오류)는 "유효하지 않은 데이터"와 동일하게 `null` 처리됨 — 로그는 없음(콘솔 로그 금지 규칙과는 별개로, 사용자 피드백 자체가 없음). 실제 에러와 "저장 없음"을 구분 못 해 디버깅이 어려움.
- `connectCloud()`는 동적 import(CDN, git-ignored config) 의존이라 **단위테스트 불가능** — 코드 리뷰로만 확인: 설정 없거나 import 실패 시 `null` 반환(catch-all)하는 로직은 맞음. 단, catch-all이 **모든** 에러(예: `createClient`가 던지는 설정 오류, JSON 문법 오류 등)를 동일하게 "클라우드 기능 없음"으로 뭉개버려 실제 설정 실수와 "설정 안 함"을 구분 못 함 — 온보딩 문서(`docs/cloud-save-setup.md`) 검증 시 설정 오타를 만들어 재현 필요.
- **로그아웃 후 상태 잔존 리스크**: `cloudActions.logout`은 `cloudSave = null`로 초기화하지만, `main.js`의 `view.hasSave`는 그 시점 `hasSave(cloudSave)`로 재계산됨(직접 확인 필요) — 로그아웃 직후 로컬 저장이 남아있다면 "이어하기"가 로컬 세이브로 정상 동작하는지, 혹은 로그아웃 전 클라우드에서 당겨온 진행 상황이 로컬에 실수로 반영되어 남는지 **수동 확인 필요** (테스트 없음).
- **동시 로그인(다른 기기) 시 `pickNewest`의 `savedAt` 비교**는 유닛테스트됨(`pickNewest`) — 그러나 기기 간 시계 오차(클라이언트 `Date.now()` 신뢰)로 인한 최신판 오판 리스크는 설계상 존재 — 문서화만 되어 있고 테스트/완화책 없음. 저사양 리스크지만 "다른 기기에서 이어하기"가 핵심 기능이라 최소 1회 수동 시나리오 필요.
- `saves.sql`의 RLS는 select/insert/update 정책만 있고 **delete 정책이 없음** — 현재 앱에 삭제 기능이 없어 당장 문제는 아니나, 향후 "계정 탈퇴/세이브 초기화" 기능 추가 시 이 SQL이 먼저 갱신되어야 함(현재는 delete 자체가 RLS 기본값(거부)이라 안전한 방향의 누락).
- `accountHtml`의 닉네임/메시지는 `escapeHtml`로 이스케이프됨 — **XSS 없음** (코드 확인 결과 공백 아님, 우려 해소).
- 저장 데이터 크기 제한(`pg_column_size(data) < 16384`)은 SQL 레벨에만 있고, 클라이언트 쪽에는 대응하는 사전 검증/에러 메시지가 없음 — 세이브가 16KB를 넘는 시나리오는 현재 스키마로는 사실상 불가능하지만, 향후 필드 추가 시 조용히 push 실패로만 나타남(위 "침묵 실패"와 동일 계열 리스크).

### 픽셀아트/상점 정렬
- 자동화 대상 아님(좌표/시각 결과물) — 코드 레벨 리스크는 낮음. 다만 `tools/art/vessels.mjs` 생성기의 출력이 실제 `styles.css`에 반영된 최신본인지(생성기 재실행 후 diff 없는지) 커밋 로그로는 확인되나 회귀 방지용 스냅샷 테스트는 없음 — 생성기를 건드리는 다음 변경에서 수동 재확인 필요.

## 5. 권고 사항 (블로커/컨선)

1. **블로커** — 클라우드 세이브: Supabase 프로젝트 및 Kakao 앱이 아직 생성되지 않아 실제 로그인/동기화 경로가 한 번도 실행되지 않음. 완료 조건 문서도 없음. `/story-readiness`로 완료 조건부터 정의하고, 환경 준비 후 세션 3을 실행해야 "완료"로 볼 수 있음.
2. **컨선** — `pushSave`가 예외를 던질 때(reject)만 알림 없이 묻힘. `false` 반환은 이미 토스트로 알림. `.catch`에서도 같은 토스트를 띄우고, 실패 분기 테스트 추가 제안.
3. **컨선** — 픽셀아트/상점 정렬 스크린샷에 "리드 sign-off"가 별도로 기록되어 있는지 파일 자체로는 확인 불가 — sign-off 기록 위치를 확인/보강 필요.
4. **스모크 체크 미실행** — `production/qa/smoke-*.md` 부재. 수동 QA 착수 전 `/smoke-check` 먼저 실행 필요 (본 작업 범위 밖, 별도 실행 요청).
